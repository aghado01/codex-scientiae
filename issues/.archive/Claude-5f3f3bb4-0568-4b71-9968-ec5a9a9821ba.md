Agreed on the principle, and I'd sharpen it: **the manifest should publish exact extents on orthogonal axes and let the reader supply its own constant — not supply a constant it can't know.** Deleting `tokens_est` was the right call. But the column that's actually dead weight is `char_count`, not the token estimate.

Across all 31 sections, `byte_width / char_count` ranges **1.0000 → 1.0065**. A 0.65% spread. It carries no decision-relevant information beyond `byte_width`, and that's structural, not incidental: the math register's own glyph→control-sequence canonicalization drives math to pure ASCII, so post-register the two columns converge across the whole corpus by construction. ## Recommendation

Replace `char_count` with `word_count` — whitespace-delimited runs, exact, no constants:

- Every BPE family pretokenizes on whitespace/punctuation before merging, so word count is a genuine **floor** on token count, not a guess. The reader calibrates `tokens/word` once against its own tokenizer and reuses it. That's the agnostic contract you're after: you publish the invariant, they own the conversion.
- `(bytes, words)` as a pair is strictly more informative than either alone. 3 KB of prose and 3 KB of dense LaTeX cost wildly different amounts in *every* tokenizer, and the ratio separates them — a single scalar cannot.

Optionally add `math_frac` (bytes inside `$…$`/`$$…$$`). It spans **0% → 81%** here, and it's the corpus's actual tokenization pathology. It's also not redundant with `bytes/word` — the two axes come apart: "Oriented matrices" is 47% math at 5.0 B/word (many tiny inline `$A$`), while "Background material" is 59% math at 10.3 B/word (long display blocks). Symbol-dense and display-dense both fragment badly, for different reasons. And it's derivable from the register's own delimiters, so it costs nothing new conceptually.

**Caveat worth stating in the manifest rather than hiding:** word count assumes whitespace-delimited script. It degrades for scriptio continua (CJK), where `bytes/word` would explode. For an English+LaTeX arXiv corpus it holds, but it's an assumption, not a universal.

If you want a step up in predictiveness later, running a *published, frozen* pretokenizer regex and emitting a pretoken count is auditable in a way `bytes/4` never was — you'd be publishing which regex you used, not guessing a merge table. More machinery than it's worth right now, I think.

# what is "label index" again?

A second record type in `.toc.jsonl` that gives every **labeled object** in the paper its own byte address — not just every section.

Your md renders 74 bold result-headers (`**Theorem 2.1.**` at byte 10740, `**Definition 2.3.**` at 12152, `**Lemma 2.7.**` at 14866, …). Each would get a record:

```json
{"kind":"theorem","number":"2.1","label":"thm:weakfactor","byte_start":10740,"byte_end":11208,"section":"column-reduction-of-non-branching-matrices"}
```

**Why it matters:** the document cross-references itself 208 times. When the text says "by Theorem 2.4," that's plain text — the reader has no address for it. Today, following that reference means loading the whole enclosing section: results live in sections up to 9,947 bytes, so you pull ~10 KB to reach maybe 400 bytes of theorem. The index makes the referenced object directly addressable.

**One correction to how I framed this earlier.** I said latex-ingest was discarding the reference graph — that's too strong. It's resolving references into *numbers* correctly; this scan turned up only a couple of misses (`from  2.17`, plus the `proof of  2.1` heading). So the work isn't recovering lost data, it's **promoting plain-text numbers that are already correct into addresses**. Smaller job than I implied.

It fits the rule we landed on: it's pure index — what exists and where — with no scoring. `kind` is descriptive (`theorem`/`definition`/`lemma`), which is also why it's the honest answer to the math-extraction question that `math_frac` was only approximating.

The cost is that it needs latex-ingest to record md byte offsets during emission, since the labels live in the `.tex` and the addresses live in the `.md`. The emission walk you extracted as a shared primitive is the hook point.

## The immutability claim needs enforcement, not just convention

`-ReuseSource` as I built it trusts that `{slug}-src/` exists with `.tex` files in it — it doesn't verify the tree still matches the tarball. And I documented "preserves hand-edits to staged source" as a *feature*. Those two can't both hold: either source is immutable or it's editable scratch.

## Run identity: put the provenance in a manifest, the sugar in the name

```powershell
    $Text = [regex]::Replace($Text, '@@L(?:MATH|DISP)\d+@@', { param($m)
        if ($script:LtxMathStore.Contains($m.Value)) { $script:LtxMathStore[$m.Value] } else { $m.Value } })
}
return $Text
```

Nesting deeper than 8 → loop exits with placeholders intact. Placeholder not in the store → left verbatim. Either way the function returns as if it succeeded.

**Is either cause inherent?** No. Both are invariants of a store *this code entirely controls* — it created every placeholder and knows the nesting depth. Nothing about author LaTeX forces a leak.

**So it's category 1: removable.** And the sharpest part — **the function already knows it failed.** Its own loop condition is evaluated on exit; if placeholders remain after 8 passes, `$Text -match '@@…@@'` is still true at that moment. The information exists and is discarded, and then reconstructed 400 lines downstream by counting the damage in the output.

The fix is a few lines at the restore boundary: if placeholders remain, that's a converter bug — throw, or flag it into the run record. The downstream sentinel then becomes what it should have been, a backstop against "impossible," rather than the primary detector.

Worth noting the scope is wider than this one function: there are **five placeholder families** — `ALG`, `VERB`, `LMATH`/`LDISP`, `FIGSLOT`, `EPSSLOT` — each created by its own store, and I've only traced one restore path. None of them has a completeness check that I found. Same trace on the other four is the obvious next step, and I'd expect the same answer, though I haven't verified it and shouldn't assume.

Your framing generalizes past this too: **a guard is evidence about its upstream.** When the upstream cause is internal state the pipeline owns, the guard is misplaced detection. When it's genuinely external — malformed author input, a missing figure file — it's real defense and belongs where it is. That's a clean discriminator, and unlike my regex scan it gives an answer you can act on rather than a list to eyeball.

Want me to take the restore-boundary assertion and trace the other four families? It's small, and it converts the sentinel from primary detection into a backstop — which is the shape you want before the sentinel gate gets rebuilt into the standalone lane.

Every one is **store-driven** — it establishes *"every stored item was written out."* The invariant that matters is **text-driven** — *"no placeholder remains."* Those aren't the same statement, and store-driven restoration is structurally blind to the gap: a placeholder in the text but missing from its store is never visited, never replaced, never reported.

Which means the md-bundle sentinel is **the only text-driven check in the entire pipeline**, and it's at the very end. That's not five bugs, it's one direction error repeated five times, with the detection displaced to the last possible moment.
