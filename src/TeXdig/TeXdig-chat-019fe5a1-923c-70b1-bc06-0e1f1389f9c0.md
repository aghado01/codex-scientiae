# what would latex parsing look like in python

For this repository, Python LaTeX parsing should be a typed pipeline—not a line-for-line translation of the current regex transforms.

```text
source files
  → confined \input/\include graph
  → lossless syntax tree with source spans
  → document IR
  → macro/counter/reference passes
  → Markdown + docstream/refgraph/oracle sidecars
```

The major conceptual split is:

1. Syntax parsing: commands, groups, environments, comments, verbatim, math.
2. TeX semantics: macro expansion, counters, labels, citations, theorem models.
3. Codex lowering: Markdown, math register, diagram store, evidence sidecars.

A minimal front end could look like this:

```python
from dataclasses import dataclass, field
from pathlib import Path
from typing import Any

from pylatexenc.latexwalker import (
    LatexWalker,
    LatexCharsNode,
    LatexCommentNode,
    LatexEnvironmentNode,
    LatexGroupNode,
    LatexMacroNode,
    LatexMathNode,
    get_default_latex_context_db,
)
from pylatexenc.macrospec import std_macro


@dataclass(frozen=True, slots=True)
class SourceSpan:
    path: Path
    char_start: int
    char_end: int


@dataclass(slots=True)
class Node:
    kind: str
    span: SourceSpan
    raw: str
    attrs: dict[str, Any] = field(default_factory=dict)
    children: list["Node"] = field(default_factory=list)


def latex_context():
    context = get_default_latex_context_db()
    context.add_context_category(
        "codex-scientiae",
        prepend=True,
        macros=[
            std_macro("section", "*[{"),
            std_macro("subsection", "*[{"),
            std_macro("label", "{"),
            std_macro("ref", "{"),
            std_macro("eqref", "{"),
            std_macro("cref", "{"),
            std_macro("cite", "[[{"),
            std_macro("includegraphics", "[{"),
        ],
    )
    return context


def parse_file(path: Path) -> tuple[str, list[Node]]:
    source = path.read_text(encoding="utf-8")
    parsed, _, _ = LatexWalker(
        source,
        latex_context=latex_context(),
        tolerant_parsing=True,
    ).get_latex_nodes(pos=0)

    def lower(node) -> Node:
        span = SourceSpan(path, node.pos, node.pos + node.len)
        raw = source[node.pos : node.pos + node.len]

        if isinstance(node, LatexCharsNode):
            return Node("text", span, raw, {"text": node.chars})

        if isinstance(node, LatexCommentNode):
            return Node("comment", span, raw)

        if isinstance(node, LatexMathNode):
            return Node(
                "math",
                span,
                raw,
                {"display": node.displaytype == "display"},
            )

        if isinstance(node, LatexMacroNode):
            args = [
                lower(arg)
                for arg in (node.nodeargd.argnlist if node.nodeargd else [])
                if arg is not None
            ]
            return Node(
                "command",
                span,
                raw,
                {"name": node.macroname},
                args,
            )

        if isinstance(node, LatexEnvironmentNode):
            return Node(
                "environment",
                span,
                raw,
                {"name": node.environmentname},
                [lower(child) for child in node.nodelist],
            )

        if isinstance(node, LatexGroupNode):
            return Node(
                "group",
                span,
                raw,
                children=[lower(child) for child in node.nodelist],
            )

        # Unknown constructs survive verbatim and become evidence.
        return Node("unsupported", span, raw)

    return source, [lower(node) for node in parsed]
```

Then the actual converter becomes an explicit series of passes:

```python
syntax = parser.parse(source_graph)
syntax = macro_pass.expand_bounded(syntax)
document = structure_pass.lower(syntax)
document = counter_pass.number(document, faithful=faithful_numbering)
document = reference_pass.resolve(document, bibliography)
document = math_pass.normalize(document)
document = diagram_pass.classify(document)

result = emitter.render(document)
result.write_markdown()
result.write_docstream()
result.write_refgraph()
result.write_oracle()
```

This would materially improve the current design in a few ways:

- Math, verbatim, floats, and diagrams remain typed nodes; they no longer need fragile `@@LMATH12@@`-style protection markers.
- Every node retains its original file and source span.
- Unknown syntax is preserved and reported instead of silently disappearing.
- Labels and reference sites naturally become graph nodes and edges.
- Transformations operate locally on nodes, so regex remains useful inside handlers without acting as the document parser.
- Macro expansion can retain both invocation and definition provenance, with depth, cycle, and expansion-budget limits.
- Multi-file input can be recursive while retaining per-file provenance and rejecting cycles or paths escaping the deposit root.

For the parser library, I would begin with `pylatexenc==2.11`: it exposes commands, environments, math nodes, and original source positions, while explicitly remaining a markup parser rather than a full TeX engine. Version 2.11 is the current stable release; 3.0 remains beta, so pinning 2.11 avoids migration-time API churn. [pylatexenc documentation](https://pylatexenc.readthedocs.io/en/latest/latexwalker/), [PyPI release history](https://pypi.org/project/pylatexenc/)

`plasTeX` is worth a corpus spike because it expands macros into a DOM and already models counters and labels. That could eliminate more custom semantic code, but its normalization and package behavior would need testing against this project’s raw-math fidelity requirements. [plasTeX DOM documentation](https://plastex.github.io/plastex/plastex/module-plasTeX-DOM.html)

I would migrate incrementally:

1. Add a Python parser that emits a shadow syntax/docgraph sidecar without changing Markdown.
2. Replace [tex-docgraph.ps1](<D:/aghado01/codex-scientiae/src/latex-ingest/tex-docgraph.ps1:57>) first; it is the cleanest AST-shaped seam.
3. Port structural lowering and reference collection.
4. Port bounded macro expansion and counters last—the genuinely TeX-semantic parts.
5. Keep source-deposit, batch execution, rendering, and audit contracts stable behind a thin PowerShell wrapper calling `python -m latex_ingest`.

The important point is that Python would not automatically solve TeX semantics. Its real payoff would be replacing the monolithic string-rewrite state in [ConvertFrom-Latex](<D:/aghado01/codex-scientiae/src/latex-ingest/latex-ingest.ps1:1714>) with a lossless tree and auditable passes.

# so would the unified-latex allow for a bib to be expanded from the source macros

Yes—but specifically at the LaTeX/`.bbl` layer, not as a complete BibTeX/Biber replacement.

| Bibliography form | What unified-latex can do |
|---|---|
| Inline `thebibliography` | Parse and expand source-defined macros |
| Traditional `.bbl` containing `\bibitem` | Parse it as LaTeX and expand macros harvested from the main source |
| `.bib` fields containing `\MyMacro` | Expand them only after a separate BibTeX parser extracts the field values |
| BibTeX `@string` macros | No; those belong to BibTeX syntax |
| biblatex/Biber `.bbl` containing `\entry`, `\field`, etc. | Parse structurally, but not reproduce biblatex’s rendering semantics automatically |
| Citation sorting, style application, name formatting | Requires BibTeX, Biber, or citeproc |

For example:

```latex
% main.tex
\newcommand{\JMLR}{Journal of Machine Learning Research}
```

```latex
% traditional paper.bbl
\bibitem{smith}
Smith. A useful paper. \emph{\JMLR}, 2025.
```

The intended pipeline would be:

```text
resolved main.tex
  → parse
  → listNewcommands()
  → build macro signatures and substitution bodies

paper.bbl
  → parse using those signatures
  → attach macro arguments
  → expandMacrosExcludingDefinitions()
  → bibliography AST with \JMLR expanded
```

The `unified-latex-util-macros` package provides `listNewcommands()`, `newcommandMacroToSubstitutionAst()`, and `expandMacrosExcludingDefinitions()`. It handles LaTeX-style and xparse-style command definitions, but explicitly does not discover plain `\def` definitions. [Macro utility documentation](https://www.npmjs.com/package/%40unified-latex/unified-latex-util-macros)

For this project we would add adapters for the extra forms the current collector already understands:

- `\let`
- `\DeclareMathOperator`
- `\DeclarePairedDelimiter`
- bounded fixed-point expansion for macros containing other macros
- possibly plain `\def` where its argument pattern is safely recognizable

The especially important boundary is:

```bibtex
@string{jmlr = "Journal of Machine Learning Research"}
@article{x, journal = jmlr}
```

Here `jmlr` is a BibTeX macro, not a LaTeX macro. A BibTeX parser must resolve it first. Conversely:

```bibtex
@article{x, journal = {\JMLR}}
```

could be parsed by a BibTeX parser and then have the extracted field’s LaTeX AST expanded using the macro table from `main.tex`.

So unified-latex would substantially improve expansion of traditional `.bbl` and inline bibliography content. It would not eliminate the current biblatex `.bbl` bridge or the need for a real `.bib` parser.

# well between unified-latex and latex-utensils which does do bibtex, i should be able to resolve the bibtex sections as well as link them to the source document in my IR

Exactly. That combination supports a solid two-parser, one-IR architecture:

```text
.tex ── unified-latex ──→ document nodes, citations, macro environment
                                  │
                                  │ citation key
                                  ▼
.bib ── latex-utensils ─→ bibliography entries and value expressions
                                  │
                                  ▼
                         unified scholarly IR
```

The correct resolution order would be:

1. Parse the resolved `.tex` source with unified-latex.
2. Collect:

   - source macro definitions;
   - `\bibliography` and `\addbibresource` declarations;
   - citation sites and their keys;
   - active `refsection`/`refsegment` scope.

3. Parse each `.bib` with latex-utensils.
4. Resolve the BibTeX expression layer:

   - `@string` abbreviations;
   - `#` concatenation;
   - numeric and literal values;
   - built-in month abbreviations;
   - `crossref`/`xdata` inheritance as a separate semantic pass.

5. Parse each resolved TeX-valued field—title, author, journal, note—through unified-latex.
6. Expand applicable source macros in those field ASTs.
7. Join citation-site keys to bibliography-entry identities.

Latex-utensils’ grammar already distinguishes ordinary entries, `@string`, `@preamble`, concatenations, abbreviations, numbers, and fields, and assigns source locations to them. [Official BibTeX grammar](https://github.com/tamuratak/latex-utensils/blob/master/src/bibtex/bibtex.pegjs)

The IR relationship should probably be:

```text
CitationSite
  └── cites ──→ BibliographyEntry
                     └── projected_as ──→ RenderedReference
```

Those are three distinct things:

- `CitationSite`: `\citep[see][p. 4]{smith2025}` in `main.tex`.
- `BibliographyEntry`: `@article{smith2025,...}` in `refs.bib`.
- `RenderedReference`: `[17] Smith, …` from a `.bbl`, Biber, BibTeX, or CSL renderer.

A representative IR might contain:

```json
{
  "kind": "citation-site",
  "macro": "citep",
  "keys": ["smith2025"],
  "prenote": "see",
  "postnote": "p. 4",
  "scope": "refsection:0",
  "source": {
    "file": "main.tex",
    "char_start": 1842,
    "char_end": 1877
  },
  "targets": [
    {
      "id": "bib:document-123:smith2025",
      "status": "resolved"
    }
  ]
}
```

```json
{
  "kind": "bibliography-entry",
  "id": "bib:document-123:smith2025",
  "citation_key": "smith2025",
  "entry_type": "article",
  "resource": "refs.bib",
  "fields": {
    "journal": {
      "raw": "jmlr # \" Letters\"",
      "bibtex_resolved": "\\JMLR Letters",
      "latex_expanded": "Journal of Machine Learning Research Letters"
    }
  }
}
```

The important design choice is to retain all three field representations:

- `raw`: exact BibTeX source and case-protection braces;
- `bibtex_resolved`: after `@string` and concatenation;
- `latex_expanded`: after parsing and expanding TeX macros.

That prevents unified-latex normalization from accidentally destroying BibTeX capitalization semantics or source evidence.

The remaining boundary is formatting: parsing and linking establish which entry a citation denotes, but they do not reproduce a `.bst` or biblatex style’s sorting, labels, name formatting, or disambiguation. For fidelity, an existing `.bbl` should remain the authoritative rendered projection and be linked back to the `.bib` entity. Without a `.bbl`, Biber/BibTeX or a CSL renderer supplies that projection.

So yes: unified-latex plus latex-utensils can give the IR substantially richer bibliography semantics than the current `.bbl`-order `Build-CiteMap`, while preserving the source document, bibliography database, and rendered bibliography as separate evidence layers.

# my IR is immature. im trying to figure out a better way of building it that lets me build an IR as well as expand macros, expose math nodes, etc to build an IR

What you want is a source-preserving elaborated IR. The missing piece is not another parser so much as a layer between the parser AST and your semantic IR.

The important rule is:

> Macro expansion should be a relationship between nodes, not a destructive rewrite of the source tree.

### What expansion looks like

Given:

```latex
\newcommand{\norm}[1]{\left\lVert #1 \right\rVert}

Let $\norm{x+y}$.
```

The source AST conceptually contains:

```text
InlineMath
└── MacroInvocation "\norm"
    └── Argument
        └── [Text "x", Text "+", Text "y"]
```

Unified-latex’s macro expander replaces the invocation with ordinary AST nodes:

```text
InlineMath
├── Macro "\left"
├── Macro "\lVert"
├── Text "x"
├── Text "+"
├── Text "y"
├── Macro "\right"
└── Macro "\rVert"
```

Serializing that expanded tree gives approximately:

```latex
\left\lVert x+y \right\rVert
```

Unified-latex does not appear to introduce a special `Expansion` node: `expandMacros` rewrites the tree with `Ast.Node[]`. Its macro utilities provide definition discovery, substitution parsing, and expansion, but provenance needs to be supplied by your integration layer. [Unified-latex macro utilities](https://www.npmjs.com/package/%40unified-latex/unified-latex-util-macros)

That means you should wrap expansion yourself rather than adopting its mutated AST as your canonical representation.

### A useful layered design

```text
SourceGraph
    ↓ parse
Source AST
    ↓ elaborate
ExpansionGraph / Elaborated View
    ↓ lower
Semantic Document IR
    ↓ resolve/project
Markdown, refgraph, docstream, bibliography, audits
```

#### 1. SourceGraph

This is the authority for what was actually written:

```typescript
interface SourceFile {
  id: string;
  path: string;
  text: string;
}

interface SourceSpan {
  fileId: string;
  start: number;
  end: number;
}
```

Always obtain original LaTeX with:

```typescript
source.text.slice(span.start, span.end)
```

Do not reconstruct “raw source” through an AST printer. Printed AST content may be equivalent LaTeX, but it is not necessarily byte-for-byte source.

#### 2. Unexpanded syntax tree

Keep unified-latex’s AST intact as your syntax representation. Its model already distinguishes macros, environments, groups, inline math, display math, comments, whitespace, and so forth. [Unified-latex AST types](https://www.npmjs.com/package/%40unified-latex/unified-latex-types)

You do not need to copy every unified-latex node into a second home-grown syntax IR. Give its nodes stable IDs and reference them from your own records.

#### 3. Macro environment and expansion graph

```typescript
interface MacroDefinition {
  id: string;
  name: string;
  signature?: string;
  bodyAst: Ast.Node[];
  origin: SourceSpan;
  scopeId: string;
  declarationOrder: number;
}

interface MacroInvocation {
  id: string;
  name: string;
  argumentAsts: Ast.Node[][];
  origin: SourceSpan;
  environmentId: string;
}

interface Expansion {
  id: string;
  invocationId: string;
  definitionId: string;
  resultAst: Ast.Node[];

  // Source mapping for generated nodes
  origins: ExpansionOrigin[];

  diagnostics: Diagnostic[];
}
```

An expanded node can have two simultaneous origins:

- Its syntactic shell may come from the macro definition.
- Its substituted content may come from an argument at the invocation site.

Represent that explicitly:

```typescript
type Origin =
  | { kind: "source"; span: SourceSpan }
  | {
      kind: "expansion";
      invocationId: string;
      definitionId: string;
      argumentIndex?: number;
      parentExpansionId?: string;
    }
  | {
      kind: "synthetic";
      rule: string;
      inputs: string[];
    };
```

This `Origin` model is probably the most valuable primitive you can add to the immature IR.

### Math nodes

A semantic math node should retain the surface and elaborated forms:

```typescript
interface MathNode {
  id: string;
  display: boolean;

  origin: Origin;
  sourceAstId: string;

  rawContentTex: string;       // \norm{x+y}
  expandedAstId?: string;
  expandedTex?: string;       // \left\lVert x+y \right\rVert

  semanticMath?: MathExpression;
  expansionTrace: string[];
  diagnostics: Diagnostic[];
}
```

These forms are meaningfully different:

```text
rawContentTex    What the author wrote
expandedTex      Generated LaTeX after macro substitution
semanticMath     Meaning inferred from the elaborated expression
```

Do not discard `\norm{x+y}` merely because you can expand it. The named macro may carry more semantic information than its low-level expansion. For some consumers, `norm(x+y)` is better than five delimiter-oriented TeX commands.

Expansion therefore works best as a selectable view:

```typescript
expand(nodeId, macroEnvironment): ExpansionResult
lower(sourceNode, expandedView): SemanticNode[]
```

### Minimal semantic IR

I would keep the first version deliberately small:

```typescript
type Block =
  | Heading
  | Paragraph
  | Environment
  | Equation
  | Figure
  | Table

  | RawLatexBlock;

type Inline =
  | Text

```

Unknown material should remain representable. `RawLatexInline` and `RawLatexBlock` are not failures—they are what make gradual lowering possible.

Likewise, preserve a `MacroCall` even when expansion succeeds:

```typescript
interface MacroCall {
  name: string;
  arguments: string[];
  origin: SourceSpan;
  expansionId?: string;
  semanticRole?: string;
}
```

### Expansion policy

Avoid aspiring to complete TeX expansion. That effectively means implementing a TeX engine, including scoping, catcodes, conditionals, registers, and package-specific behavior.

Use bounded elaboration instead:

- Expand document-defined declarative macros.
- Expand macros with known unified-latex signatures.
- Expand inside both prose and math contexts.
- Detect cycles and enforce depth/node budgets.
- Leave unsupported procedural macros intact.
- Record diagnostics instead of dropping content.
- Cache by invocation plus macro-environment fingerprint.
- Prefer lazy expansion when only some consumers require it.

Also remember that macros can produce structure:

```latex
\newcommand{\mysection}[1]{\section{#1}}
```

So the semantic structure pass should consume the elaborated view, while retaining links to the original invocation.

### Bibliography integration

The same design fits BibTeX cleanly:

```text
BibTeX source expression
    ↓ latex-utensils
BibValue AST
    ↓ resolve @string, #, crossref/xdata
Resolved field string
    ↓ unified-latex
LaTeX field AST
    ↓ document macro environment
Expanded field view
    ↓
BibliographyEntry semantic node
```

Keep these separately:

```typescript
interface BibliographyField {
  rawBibtex: string;
  resolvedBibtex?: string;
  latexAstId?: string;
  expandedLatexAstId?: string;
  semanticValue?: unknown;
  origin: SourceSpan;
}
```

The practical migration path for your existing pipeline is therefore:

1. Introduce `SourceSpan`, stable node IDs, `Origin`, and `Diagnostic`.
2. Store unified-latex’s unexpanded AST.
3. Add a provenance-bearing expansion graph alongside it.
4. Lower only the constructs you currently need into semantic nodes.
5. Preserve everything else as linked raw LaTeX.
6. Gradually replace existing regex/rewrite stages with semantic passes.

That gives you an IR you can grow without needing to correctly understand all of LaTeX on day one.

## The central addition: elaboration

The source AST remains unexpanded. Elaboration records what an invocation means under a particular macro environment:

```typescript
interface MacroDefinition {
  id: MacroDefinitionId;
  name: string;
  signature: ArgumentSignature;
  body: SyntaxNodeRef[];
  origin: SourceSpan;
  scope: ScopeId;
  declarationOrder: number;
  dialect:
    | "newcommand"
    | "xparse"
    | "math-operator"
    | "paired-delimiter"
    | "let"
    | "def"
    | "configured";
}

interface MacroInvocation {
  id: MacroInvocationId;
  name: string;
  arguments: SyntaxNodeRef[][];
  origin: SourceSpan;
  scope: ScopeId;
}

interface Expansion {
  id: ExpansionId;
  invocation: MacroInvocationId;
  definition: MacroDefinitionId;
  environmentFingerprint: string;
  result: DerivedSyntaxNode[];
  diagnostics: Diagnostic[];
}
```

The expansion is an overlay, not a replacement. That lets a consumer choose between:

```text
author surface:  \norm{x}
expanded syntax: \left\lVert x\right\rVert
semantic form:   Norm(x)
```

All three are valuable.

Unified-latex can perform the mechanical substitution, while your layer records:

- Which invocation was expanded.
- Which definition governed it.
- Which result nodes came from the definition body.
- Which result nodes came from each invocation argument.
- Nested expansion ancestry.
- Cycles, unsupported forms, and budget exhaustion.

## Math becomes straightforward

Math is discovered by unified-latex before any placeholder machinery is needed:

```typescript
interface MathNode {
  id: MathId;
  mode: "inline" | "display";
  origin: Origin;
```

# can we fill in the gaps with the raw stream, shouldn't be to hard as a preprocessing step

Yes. The probe shows `parseMinimal()` already provides most of the raw stream we need. We should avoid writing another LaTeX lexer unless specific gaps force it.

The useful arrangement is two synchronized views:

| View | Provides |
|---|---|
| Original source buffer | Exact bytes, CRLF, spacing, delimiters and comments |
| `parseMinimal(source)` | Positioned macros, groups, math regions, environments and unconsumed token sequence |
| Processed parse | Attached arguments, known macro signatures, math context and environment semantics |

For example, the minimal parse retained:

```text
\pair       [41,46)
{x}         [46,49)
```

The processed parse produced:

```text
Macro "\pair"
└── Argument "{x}"       // wrapper has no position
    └── String "x"       // still has [47,48)
```

So the information has not really disappeared. Argument processing reorganized it. We can join the processed node back to the minimal stream at the macro’s starting offset and recover the consumed raw extent.

## Proposed source overlay

```typescript
interface RawSource {
  sourceId: string;
  text: string;
  lineStarts: number[];

  minimalAst: Ast.Root;
  nodesByStart: Map<number, Ast.Node[]>;
  groups: BalancedRegion[];
  brackets: BalancedRegion[];
}

interface SourceAttachment {
  nodeId: string;

  // Parser token itself: normally just "\pair"
  tokenSpan: SourceSpan;

  // Whole invocation: "\pair[y]{z}"
  surfaceSpan: SourceSpan;

  argumentSpans: Array<SourceSpan | null>;
}
```

Then:

```typescript
rawText(attachment.surfaceSpan)
// => "\\pair[y]{z}"
```

No serialization is involved.

## Processing sequence

```javascript
const rawAst = parseMinimal(source);

// First semantic parse discovers declarations.
const discoveryAst = parse(source);
const declarations = listNewcommands(discoveryAst);

// Reparse with discovered signatures.
const parser = getParser({
  macros: buildMacroInfo(declarations),
  environments: configuredEnvironments
});
const processedAst = parser.parse(source);

// Reconcile processed nodes against rawAst/source.
const sourceMap = attachRawSpans(processedAst, rawAst, source);
```

This is partly preprocessing and partly reconciliation:

1. Raw indexing happens first and is signature-independent.
2. Argument ownership is assigned after macro/environment signatures are known.

Trying to assign invocation spans entirely before discovering signatures would make the raw scanner guess whether `[x]`, `{x}`, or the next token belongs to a macro.

## What `parseMinimal()` already covers

The live probe confirmed it retains full positions for:

- Brace groups, including delimiters.
- Inline math regions.
- Environment regions, including `\begin` and `\end`.
- Macro control sequences.
- Text, whitespace and comments.
- Raw optional arguments as positioned `[`/content/`]` nodes.
- Original UTF-16 offsets across CRLF input.

That means the custom logic can remain narrow:

- Index nodes by position.
- Pair bracket delimiters that minimal parsing leaves as strings.
- Walk raw siblings from a macro anchor according to the processed arguments.
- Distinguish missing optional arguments from explicit empty arguments.
- Compute the union span for each invocation.
- Preserve source slices independently of `printRaw`.

The raw source is necessary because `printRaw` normalized the CRLF input and transformed forms such as:

```latex
x_1 → x_{1}
```

## Expansion provenance

The same overlay resolves expansion origins elegantly:

```typescript
interface ExpandedNodeOrigin {
  expansionId: string;

  producedFrom:
    | { kind: "definition"; span: SourceSpan }
    | { kind: "argument"; invocationSpan: SourceSpan; argument: number };
}
```

Our expansion probe already showed those two position families naturally:

```text
\left\lVert       positions in macro definition
x+y               positions at invocation site
\right\rVert      positions in macro definition
```

The overlay can recognize and formalize that rather than expecting expanded text to have one contiguous source span.

## Remaining hard cases

The scanner should stop at lexical recovery, not attempt TeX execution. The cases needing explicit handling or fallback are:

- `\verb` and verbatim environments.
- Comments between a macro and its arguments.
- Empty `{}` and `[]` arguments.
- Delimited and token-style xparse arguments.
- Catcode-changing regions.
- Plain `\def` parameter syntax.
- Malformed/unclosed groups.

For unsupported cases, retain a raw span plus a diagnostic. That is still a valid IR result.

So yes: a source tape plus `parseMinimal()` should fill nearly all the fidelity gaps cleanly. It turns the problem from “write another parser” into “align the raw and elaborated views by source offset.”

```typescript
  | "unsupported-definition"
```

## Source coverage

Maintain a coverage ledger over the raw tape:

```typescript
interface SourceCoverage {
  span: SourceSpan;
  disposition:
    | "preserved"
    | "consumed-by-expansion"
    | "declaration"
    | "trivia"
    | "raw-fallback"
    | "unclaimed";
  entityId?: string;
}
```

An expansion consumes the complete invocation span even though its produced nodes may point partly into the macro definition:

```text
invocation: \norm{x}                  consumed by expansion
definition nodes: \left\lVert ...     originate in definition
argument nodes: x                     originate at invocation
```

Therefore coverage and origin must remain separate concepts:

- Coverage answers: “Did we account for every piece of source?”
- Origin answers: “Where did this produced node come from?”

## Recovery granularity

Recover at whole syntactic boundaries whenever possible:

1. Argument.
2. Macro invocation.
3. Environment.
4. Math region.
5. Only finally, arbitrary source range.

Avoid inserting isolated raw characters into an expanded AST. Falling back for an entire invocation gives downstream consumers a coherent opaque object rather than syntactic debris.

A useful recovery ladder is:

```text
complete expansion
    ↓ failure
structured opaque macro with recovered arguments
    ↓ failure
minimal-AST subtree
    ↓ failure
exact raw source slice
```

That ensures ingestion never silently drops content.

## Practical sequence

```javascript
const rawTape = indexRawSource(source, parseMinimal(source));

const discovery = parse(source);
const signatures = discoverSignatures(discovery);

const parsed = parseWithSignatures(source, signatures);
const definitions = collectExpansionReadyDefinitions(parsed);

const expanded = boundedExpand(structuredClone(parsed), definitions);

const defects = auditElaboration({
  source,
  rawTape,
  parsed,
  expanded
});

const recovered = fillDefectsFromRaw(expanded, defects, rawTape);
```

The bounded expansion should preserve the old workflow’s fixed-point behavior:

```text
pass 1: \aaa{x} → \bbb{x}
pass 2: \bbb{x} → [x]
pass 3: unchanged; stop
```

Record each pass rather than treating the final tree as unexplained output.

This approach lets the libraries handle the normal case, while the raw stream becomes an evidence-backed escape hatch for the strange LaTeX that motivated the old recovery machinery. It also means you can start probing real documents before finishing a comprehensive source-mapping layer.

- Valid KaTeX.
- Faithful to the author’s notation.

## What canonicalization means here

```latex
α             → \alpha
a \ge b       → a \geq b
\dfrac{a}{b}  → \frac{a}{b}
```

```latex
\to               ≠ \longrightarrow
\mathbb{R}        ≠ R
```

```javascript
katex.renderToString(content, {
```
